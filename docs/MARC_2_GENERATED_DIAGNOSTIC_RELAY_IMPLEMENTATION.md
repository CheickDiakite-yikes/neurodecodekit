## Exact Path

Every qualification path performs the same ordered composition:

1. Build the registered profile-A 1,227-row generated blueprint.
2. Convert every row into an exact central-directory `EntrySpec`.
3. Materialize only central-directory and trailer bytes, using ZIP64 where
   offsets or sizes exceed 32 bits.
4. Parse all 1,227 entries through the exact MARC1 parser.
5. Compose the live-shaped manifest through the exact MARC1 producer.
6. Replace only the three generated `transport_body_sha256` values with the
   VR2 fixture values.
7. Pass the object to VR6, which invokes VR2 before selection.
8. Retain only aggregate success fields or the outer VR6 and nested VR2 codes.

Member local headers and member payloads are never materialized or read.
Generated local intervals are deterministic, nonoverlapping, and below the
central-directory offset.

## Order-Normalization Finding

The generated canonical and reversed paths select the same 16 subjects and 96
run bundles. VR6's existing `selection_identity_sha256` differs between those
paths because it deliberately includes the canonical hash of the complete live
source, whose entry order differs.

VR8B does not alter that upstream provenance behavior. It computes a separate
`normalized_selection_identity_sha256` over the selected generated members,
structural sizes, CRC values, split roles, and aggregate summaries while
excluding transport order, local offsets, and source hashes. Both orders yield
the same normalized digest:

```text
812ecbe8f402ae49eab22f166964390b8024639e0afc8b793f9fe89105f20923
```

This keeps transport provenance distinct from cohort identity rather than
silently redefining VR6.
